# Learning and review method

## What is recorded

Each content topic has a question file and three test files. Put all numbered
prompts and learner answers first. Put learner corrections in a separate section.
Put all assistant feedback in the final section, with one review per question.
Keep extra practice and cohort questions separate from the scored answers.
The main README is a summary with links to the underlying evidence.

Present the full topic's questions in one batch unless the learner asks otherwise.
Include all source subparts. Wait for the full submission before giving feedback.
Answers can arrive in several messages. Keep the attempt in progress until the
learner submits it for review. Record confidence and help used for the batch,
with any exceptions beside the relevant answer.

Keep every answer in full. Correct only clear spelling, typing, punctuation
and spacing errors. Preserve wording, order, meaning and factual claims.
Do not fill gaps or improve an answer. Leave unclear words unchanged.
Label spelling edits. Preserve earlier submissions and existing Git history.
Spelling changes do not count as learner corrections or change the score.

Use Test 1 after reading. Use Test 2 after a gap, then Test 3 after another gap.
Choose the gap to suit recall. No fixed dates or weekly deadlines are required.
Record the actual gap in the attempt file when known. Attempt the same questions
with earlier answers, reviews and reading closed. Mark any lookup, hint or
other help. Checking the text afterwards is part of learning.

A corrected explanation belongs to the current attempt. It is not a new memory
test. A later attempt starts with an empty answer field. Preserve all attempts.
If further practice is needed, add another dated or numbered attempt and link
it from the topic; do not overwrite earlier results.

## Scoring

The unit is one numbered Bitshala question, including its substantive subparts.
The question set is fixed across the three attempts. Current counts were checked
against the course: 8 introductory questions, 10 for Core/keys/addresses, and
8 in each other topic.

| Review outcome | Meaning | Counts as fully correct |
| --- | --- | --- |
| Correct | All substantive parts are accurate and the reasoning supports the answer. | Yes |
| Partial | Some substantive parts are correct, but a gap or error remains. | No |
| Incorrect | The central explanation is wrong. | No |
| Unanswered | The learner left this question unanswered in a submitted attempt. | No |
| Needs verification | The reviewer cannot yet establish a fair outcome. | No final score yet |

For opinion questions, assess factual accuracy, reasons and trade-offs. A
different defensible opinion is not an error. A justified challenge to a false
premise can be correct. Review the complete question in the source before scoring.
For practical tasks, request the learner's actual demonstration or evidence.

Show the count in the README only when all questions have been reviewed.
The denominator includes unanswered questions in a submitted attempt.
Until submission, use Not started or In progress. Until review is complete,
use Awaiting review or Review incomplete. Never interpret an empty template
as a completed zero-score test.

Record partial, incorrect and unanswered counts beside the fully correct count.
If help was used, label the attempt assisted in both its file and the README.
These scores describe submitted work; they are not an official grade or proof
of independent ability. Do not revise an original score after corrections.
Use the next attempt to measure later recall.

## Feedback and application

Explain the precise error, the missing reasoning and how to check the correction.
Use specific source links. Give a manageable hint or a worked example when useful.
Keep the result, all numbered reviews, sources and next action in the final
assistant feedback section. Do not insert feedback between learner answers.
The learner writes the corrected explanation and the reason for the change.

Include occasional new examples or practical tasks to check application.
Record these under Extra practice and keep them outside the repeated-question
score. Retest unresolved gaps even after the third attempt.

## Saving to GitHub

Save the answers and feedback in the correct test file after review.
Update the README from its per-question outcomes.
Check answer completeness, spelling edits, feedback order and score counts.
Inspect Git status and review the scoped diff. Stage explicit file paths.
Commit and push the learning changes to origin unless the learner asks to
keep them local. Preserve unrelated work and never force-push.
Confirm the push result and link to the saved test.

## Why this method

Recall practice and spacing have research support. Clear explanations and
examples help a beginner get started. Feedback identifies errors. Applying an
idea to a new case gives additional evidence about understanding.

- [Research review: spacing and retrieval practice](https://doi.org/10.1038/s44159-022-00089-1)
- [Make It Stick: learning strategies](https://www.makeitstick.com/learning-strategies)
- [Learning How to Learn](https://www.coursera.org/learn/learning-how-to-learn)
- [Scott Young: examples, practice and revised learning advice](https://www.scotthyoung.com/blog/2023/01/17/revised-views-learning/)
- [James Clear: specifying when and where to act](https://jamesclear.com/implementation-intentions)

The exact number of attempts and the gap lengths are practical choices. Adjust
them using the learner's results. Keep records short enough to leave time for
reading, practice, experiments and cohort discussion.
